## Authz contract (two layers)

**Layer 1 — action edge (primary, authoritative).** Every mutation and sensitive
read goes through a Next.js Server Action backed by Drizzle. Drizzle connects via
`DATABASE_URL` as the `postgres` role, which has `BYPASSRLS` (verified
`pg_roles.rolbypassrls = true`). This gate **cannot be bypassed from the browser**
and is the authoritative authorization for every table. Configured in
`db/index.ts` (guarded by `import "server-only"`).

**Layer 2 — RLS (defense-in-depth backstop).** Every table has
`ENABLE ROW LEVEL SECURITY`: <!-- fact:rls_enabled_tables -->63<!-- /fact -->
distinct tables are declared with it across `db/*.sql` and `db/migrations/*.sql`,
and none is ever disabled. That is the DECLARED count, generated by
`pnpm facts:write`; the live catalog reading is `__tests__/rls/*`, which asserts
against `pg_class.relrowsecurity` and is the only authority on what is actually
enabled in a running database. RLS only governs the PostgREST surface (the
supabase-js anon / publishable key). It never affects the action edge. Contract
documented in `db/migrations/0086_track_rls_in_migrations.sql` (connection-role
invariant) and `db/migrations/0105_rls_defense_in_depth.sql` (authz contract).

**Implication.** RLS is enabled everywhere; the "gap" is not disabled RLS but
tables that are RLS-enabled with **zero permissive policies** (= deny-all to
PostgREST). That is safe *because* the app never reads those tables through the
anon-key/PostgREST surface — only via the service-role Drizzle connection.

## Sensitive set — backstop status

The handoff flagged `profiles, ownerships, pets, pet_events, pet_identifications,
welfare_*, share/scan tokens`. All are RLS-enabled with owner/reporter-scoped
read policies. Notes:

- **pet_identifications / pet_transfers** — PII (microchip/ISO/tattoo, Ley 25.326)
  and transfer records. RLS-enabled since `0086` but their SELECT policies were
  only added in `0105_rls_defense_in_depth.sql` (a real backstop gap between 0086
  and 0105, now closed). **No write policies** — inserts/updates rely on the
  action edge (service-role bypass). Acceptable under the Layer-1 contract.
- **"scan tokens"** — there is no separate table; scans are `pet_events` rows with
  `event_type = 'credential_scanned'`, `author_role = 'scanner'`, inheriting
  `pet_events` RLS. Retention: 90-day purge (`app/api/cron/purge-scan-events`,
  trigger exception in `0104_scan_events_retention.sql`, audited).

## Backstop gap assessment (WS-A finding)

There is **no missing RLS migration to add** — 0086 enabled RLS on all tables and
0105 added the defense-in-depth read policies for the sensitive PII tables. The
remaining "gaps" (deny-all tables) are intentional and safe under the Layer-1
contract. The residual risk is entirely at the action edge: if a future code path
queries a table via the anon-key/PostgREST surface, the deny-all posture protects
it; if the action edge itself has a bug, RLS on the owner-scoped tables is the net.

**Verified by:** `__tests__/rls/coverage.test.ts` (structural: fails CI if a public
table is unclassified or an `RLS_REQUIRED` table loses catalog-level RLS) and
`__tests__/rls/matrix.test.ts` (behavioral: per-role allow/deny probes).
